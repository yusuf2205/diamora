# Decisions (ADR log)

Rule: if a choice is small, decide, write it here, move on. Newest decisions are appended at the end.
Status: ✅ decided · ⚠️ needs owner input (see "Open owner actions" at the bottom).

| # | Decision | Why |
|---|---|---|
| D-001 | **NAS is the source of truth.** PostgreSQL, Redis, MinIO, API, WebSocket, bot worker, web, logs, backups all run on our NAS in Docker. Phones are clients only. | Business requirement. |
| D-002 | **External services only as transport:** Telegram Bot API (registration, one-time login codes, notifications) and Yandex MapKit (map tiles on the phone). No business database/storage in any cloud. Push payloads / Telegram messages never contain money, collateral details or full addresses. | Telegram/Yandex are unavoidable for the chosen UX; keep data out of them. |
| D-003 | **Single organisation (no multi-tenancy).** No `organizationId` columns. | Home business; halves the code and the test surface. Adding tenants later = one migration + query scope (accepted cost). |
| D-004 | **Two roles only: `ADMIN`, `WORKER`.** One `Role` enum; permission = role check (`@Roles('ADMIN')`). Courier/warehouse/QC roles are later additions to the same enum. | Simple first. |
| D-005 | **Telegram Bot = interface, NestJS = business logic.** The bot runs in a separate `worker` container (same codebase/image, different entrypoint), uses **long polling** (no inbound webhook → works behind CGNAT), keeps conversation state in PostgreSQL (`RegistrationDraft`), and only translates Telegram updates ⇄ `RegistrationService` calls. | Bot restarts never lose a half-filled registration; logic is unit-testable without Telegram. |
| D-006 | **Outgoing Telegram messages go through a DB outbox** (`Notification`, channel `TELEGRAM`). The API never talks to Telegram; the bot process delivers the outbox. | API keeps no internet egress; delivery is retried and auditable. |
| D-007 | **ADMIN signs in with phone + password (argon2id). WORKER signs in with a 6-digit one-time code sent by the bot to her Telegram** (5 min, single use, max 5 attempts, stored hashed). Refresh-token rotation with reuse detection, per-device sessions, login lockout. | Workers have no passwords to forget; no SMS provider needed; we already know her Telegram chat. |
| D-008 | **Realtime = Socket.IO gateway in the API + Redis pub/sub bus.** Events are published **only after the DB transaction commits**. The bus is Redis in production (so the bot process can notify ADMIN sockets) and an in-process emitter when `REDIS_URL` is unset (tests). Clients treat events as "something changed" and refetch; the API stays the source of truth. | Required by the brief (§12–13). |
| D-009 | **Money = `BigInt` whole UZS**; metres = `Decimal(10,2)` computed in integer centimetres. Money travels as decimal strings in JSON. | No floats anywhere near money. |
| D-010 | **Immutability is enforced by PostgreSQL triggers** on `audit_logs`, `worker_ledger_transactions`, `collateral_history`, `stock_movements`, `work_assignment_status_history`, `pay_rate_changes` (no UPDATE/DELETE/TRUNCATE). Fixes are compensating rows (`CORRECTION`). | An application bug cannot rewrite history. |
| D-011 | **Stock = movements** (`StockMovement`) + materialised `StockBalance` (CHECK ≥ 0). **Materials held by a worker are derived from movements** (view `worker_material_holdings`), not a second table. | One source of truth, no double bookkeeping. |
| D-012 | **QR carries only an opaque code** (`YQ1.` + 12 base32 chars) stored in `QrEntity`; scanning calls `GET /v1/qr/:code` (ADMIN only). No personal data in the code. | Brief §14. |
| D-013 | **Maps:** Yandex MapKit (Flutter `yandex_maps_mapkit_lite`, see D-026) shows workers from GPS received via Telegram; "Call" and "Route" use `tel:` / Yandex Maps deep links (no API key needed for those). MapKit key is supplied with `--dart-define=YANDEX_MAPKIT_KEY`. ⚠️ | Brief §8. |
| D-014 | **Files:** MinIO (S3 API) on the NAS; the API proxies uploads (validates real image bytes, strips EXIF, thumbnails) and serves short-lived HMAC-signed URLs. Photos sent to the bot are downloaded by the worker process and stored in MinIO at once. PostgreSQL keeps metadata only. | Controlled access, nothing public. |
| D-015 | **MinIO upstream is archived (Apr 2026)**; official images only on `quay.io`. We pin `quay.io/minio/minio:RELEASE.2025-09-07T16-13-09Z.hotfix.7aa24e772`, keep MinIO on the internal Docker network (never public), and only use the S3 API (`StoragePort`) so it can be swapped for Garage/SeaweedFS by config + `mc mirror`. ⚠️ plan a migration in the "Improvements" phase. | Honest risk record. |
| D-016 | **Secrets never in Git.** `.env` is generated on the NAS by `infra/scripts/nas-init.sh` with random secrets; `.env.example` is the template. | Security. |
| D-017 | **Reverse proxy = Caddy.** Exactly one port is published (see D-025 for why it is plain HTTP, not 80/443). `/health/ready` and Swagger are blocked at the proxy. PostgreSQL/Redis/MinIO live on an `internal` Docker network. | Simplest secure setup on a NAS. |
| D-018 | **Toolchain pinned for stability:** Node 24, pnpm 12 (`allowBuilds` whitelist), NestJS **11** (12 is ESM-only), Prisma **6** (npm `latest` is an RC), TypeScript **5.9**, PostgreSQL **17**, Redis 7.4, Next.js 16, Flutter 3.47, grammY. | Avoid unproven majors in a money system. |
| D-019 | **Backups stay under our control:** nightly `pg_dump` (+ checksum), continuous WAL archive + weekly base backup (PITR), MinIO mirror without delete propagation, config snapshot, automatic restore-verification. NAS snapshots are configured on the NAS itself. No cloud copy unless the owner decides later (encrypted, secondary only). | Brief §57. |
| D-020 | **UI is replaceable:** Flutter is split into `core/` (network, db, realtime, theme tokens), `features/<x>/{data,application,presentation}`; screens contain no business rules and read only providers. All colours/typography come from one `AppTheme`. Backend DTOs are stable and UI-agnostic. | The owner will iterate on design after seeing screens (§61). |
| D-021 | **Registration → approval:** the bot creates `WorkerProfile(PENDING_APPROVAL)` and a **declared** collateral (`PENDING`). ADMIN approves (worker becomes `ACTIVE`, receives a personal QR, gets a Telegram message) and confirms the collateral as physically received (`HELD`). Rejection keeps the record (audit) with a reason. | A declaration is not custody. |
| D-022 | **Offline (ADMIN app):** reads come from a local Drift cache; only non-critical changes may be queued. Money, collateral, stock, issuing, acceptance and payouts require server confirmation. | Brief §56. |
| D-023 | **Build only what the milestone needs.** The Prisma schema contains the whole §58 model from M0 (schema-first); services/UI are added per milestone. No mocks in critical flows. | Simple first, but honest. |
| D-024 | **Workers are paid per 9 m kit, never per metre** (owner, 2026-09-21). The price is UZS per kit (D-027: ONE global price, 30 000 at the start). `earning = round_half_up(ratePerKit × acceptedCm / 900)`: 9/18/27 m pay exactly 1/2/3 × rate; a partly accepted kit is paid pro rata — ✅ confirmed by the owner 2026-09-21 (alternative, not chosen: whole kits only = flooring in `earningFor`). Migrations `20260921180000_rate_per_kit`, `20260921190000_global_pay_rate`. | Matches how the business prices work; the pro-rata default never pays a worker nothing for 8 good metres. |
| D-025 | **Our NAS is shared and already busy** (UGREEN DXP4800 Plus, x86_64, Debian 12, Docker 29 / Compose 5, 62 GB RAM, /volume1 9 TB; ≈30 containers of other projects; host ports 80/443 belong to the NAS, also 3000/3001/3005/3100/4100 etc.). Therefore: (1) the proxy listens on plain HTTP and publishes **one** port, `HTTP_PORT` (8088), bound to `127.0.0.1` by default; (2) internet HTTPS = **optional Cloudflare Tunnel** (compose profile `tunnel`, outbound only, works behind CGNAT — the NAS already runs such tunnels; Cloudflare then sees HTTP traffic, which stays the owner's explicit choice per D-002); (3) fixed Docker subnets 172.30.61–63.0/24; (4) no `container_name`, everything under `/volume1/docker/yusmus`; (5) one public origin (`PUBLIC_URL`) with path routing replaces the two domains. Replaces the Let's Encrypt/80/443 design. | Ports 80/443 cannot be used; avoids touching the other projects. |
| D-026 | **Map package = Yandex's official `yandex_maps_mapkit_lite`** (verified publisher maps.yandex.ru, v4.45.0), not the community `yandex_mapkit`. Lite covers map, markers, user location; route building (Full SDK) is not needed because **Route** is a deep link. Licence: free up to 25 000 monthly active users. | Official, maintained, free at our scale. |
| D-027 | **ONE global price for a 9 m kit: 30 000 UZS (owner, 2026-09-21), changeable by ADMIN at any moment, and the change applies to everybody.** Table `pay_rate_changes` (append-only: who, when, previous → new, note; current = highest `seq`; seeded with 30 000 by the migration); `GET /v1/settings/pay-rate` (ADMIN + WORKER), `PUT` (ADMIN only, 1 … 10 000 000, concurrent changes serialised by an advisory lock, same value = no-op), `GET …/history` (ADMIN). Every change is audited and broadcast as `pay_rate.changed` to ALL admin and worker screens. **Work that is not yet accepted is paid at the current price** (no rate is copied into assignments); on acceptance the amount goes into the immutable ledger and `settledRatePerKit` records the price used, so **accepted / paid work is never recalculated**. Per-variant rates were removed. Workers are not told about a change in Telegram (D-002: no money in Telegram); their app shows it live. | The owner wants one price they can change instantly for everyone; history and the ledger keep money honest. |
